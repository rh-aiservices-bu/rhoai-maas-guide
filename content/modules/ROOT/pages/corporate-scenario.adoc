= Fed Aura Capital: The Enterprise AI Gateway Scenario

A bank, a CIO mandate, and six fake models. This page is the production guide for the {maas} 3.6 product video: how the video is cut, what is said over it, the artwork it needs, and - after the curtain - exactly what was built on the cluster to make every frame possible.

The story: Fed Aura Capital, a bank with 80,000 employees, decides to kill shadow AI. No more personal Claude subscriptions, no more ad-hoc Cursor keys, no more Gemini in a browser tab. Every employee, every application, every agent reaches every model through one gate - the Red Hat AI Gateway, powered by {maas}. What each department sees, and how much it can spend, is decided by policy, not code.

This document is ordered from lowest complexity to highest. First the video, then the words over the video, then the artwork, then the demo environment that makes it all true.

TIP: All file paths and `oc apply` commands in this guide are relative to the link:{repo-url}[rhoai-maas-guide] repository root. Make sure you have cloned it and are working from its root directory (see xref:index.adoc#_getting_started[Getting Started]).

== The video

*Target: 5 minutes maximum. Voice of god (off-screen narration) throughout - no visible presenter. Screen recordings of the live environment on a real cluster; no re-enactments of the UI.*

The video runs seven scenes. Each scene lists what is on screen and what the cut should feel like.

=== Scene 1 - The mandate (0:00-0:25)

On screen: the CIO email (asset M1, full-screen), then a quick flicker of the shadow AI it kills - a browser tab with a chatbot, an IDE with a personal provider - each one stamped out.

The email is the hook. It says, in plain language, that starting next month all AI consumption goes through the Red Hat AI Gateway. Keep it under 120 words - it is read in the edit, not on camera.

=== Scene 2 - One gate for everything (0:25-1:00)

On screen: the architecture diagram (asset M2): 80,000 employees on the left, the Red Hat AI Gateway in the middle, the two model estates on the right - on-prem models on the company's own GPUs, and cloud/SaaS models (general, large-context, image generation) in external clouds.

This is the "single pane of glass" beat. Everything routes through the gateway; nothing bypasses it.

=== Scene 3 - The bank (1:00-1:30)

On screen: the Fed Aura Capital org chart (asset M3): seven divisions with their headcounts, totaling 80,000 employees.

The point: a bank is not an internet company. Most of the headcount is bankers. Each division touches different data, so each division gets a different slice of the model estate.

=== Scene 4 - Each person sees only what they are allowed (1:30-2:30)

On screen: the {rhoai} Dashboard model catalog, three logins in sequence. Log out, log back in, different models.

. As a developer - the coding models plus general purpose
. As a marketer - the public general model plus the image model
. As a credit officer - one on-prem general model, nothing else
. (Optional, ~10s) As an IT admin - all six

The platform hides what a user cannot access. No "request access" button, no greyed-out rows. The catalog is the policy.

=== Scene 5 - The admin view (2:30-3:20)

On screen: admin side of the dashboard. Two cuts:

* The subscription list - one per division, human-readable names, visible per-model hourly limits, and a description of what the tier is for.
* The usage dashboard - consumption per model across the bank. Tokens first; dollars where the platform reports model pricing (see the xref:#the_dollar_display[branch] below).

This is the CIO's dashboard: who is using what, and what it is costing.

=== Scene 6 - The developer's day (3:20-4:30)

On screen: split screen. Left: the {rhoai} Dashboard endpoints page - model name, base URL, the freshly generated API key. Right: a VS Code workbench with the Zoo Code extension.

The developer copies the base URL and key, adds an OpenAI-compatible provider called "Red Hat AI" in Zoo Code, the allowed models populate the dropdown, they write a Python hello world, it runs, and the token meter climbs in real time - input and output counted.

This is the payoff: the whole integration is copy-and-paste. The developer never sees a cluster.

=== Scene 7 - Guardrails (4:30-5:00)

On screen: a cut card - "55 minutes later..." (asset M5) - then the IT admin, same workbench style as scene 6, mid-generation: the request is rate-limited on the cloud model. The admin switches the dropdown to the on-prem Opus 5.1 and continues, uninterrupted.

The cloud budget for this hour was exhausted in real usage; the on-prem model has no such constraint. The video ends on the mandate's promise: one gate, policy decides, the work keeps moving.

Scene 5 wants cost on screen, not just tokens. There are two branches, and the video is not blocked by which one we can use:

== Talk track

Per-scene key messages and must-say points. Not a verbatim script - the narrator carries the tone, these lines carry the content. Total narration budget: ~5 minutes, ~700 spoken words.

=== Scene 1 - The mandate

* Key message: shadow AI is a risk problem, and the CIO solved it with a mandate, not a memo.
* Must say: "Starting next month, every AI conversation in this bank goes through one gateway."
* Must say: the company will not pay for, or defend, a dozen private subscriptions.

=== Scene 2 - One gate for everything

* Key message: one gateway in front of everything - on-prem models we own, and cloud models we rent.
* Must say: "Single pane of glass": one place to see, control, and bill for all AI usage.
* Must say: nothing reaches a model without passing the gateway.

=== Scene 3 - The bank

* Key message: 80,000 people, seven divisions, and data sensitivity is the axis that decides everything.
* Must say: marketing creates content - public models are fine. Credit and risk touch customer financial data - on-prem only.
* Must say: the policy is per division, and it lives in the platform, not in a wiki page.

=== Scene 4 - Each person sees only what they are allowed

* Key message: the catalog is the policy. You see what you may use - nothing else exists, from your seat.
* Must say: no greyed-out models, no "request access" - the platform hides what you cannot use.
* Must say: the same login that opens the dashboard is what authorizes every API call.

=== Scene 5 - The admin view

* Key message: the CIO's view - who is using what, how fast, and what it costs.
* Must say: each division has one subscription with per-model hourly caps; the caps encode the cost model, not the technology.
* Must say: on-prem is a sunk cost - we own the GPUs - so its caps are generous. Cloud is rented - its caps are tight.
* Must say: spend is visible in dollars, not just tokens.

=== Scene 6 - The developer's day

* Key message: integration is copy-and-paste. Base URL, API key, done.
* Must say: the developer picks a model from a dropdown that only lists what their division is allowed.
* Must say: the meter on screen is live - the gateway is counting every token of every request.

=== Scene 7 - Guardrails

* Key message: when the cloud budget runs out, the work does not stop - it moves on-prem.
* Must say: the IT admin burned through the cloud model's hourly budget in a real hour of work - the 429 is earned, not staged.
* Must say: cloud is rented, so it is capped; on-prem is sunk cost, so the fallback has room to run.
* Closing line: "One gateway. Policy decides. The work keeps moving."

== The demo environment

This is what it took to build the thing: a fully working, CPU-only replica of the Fed Aura Capital setup. No real models, no GPUs - every "model" is the llm-d inference simulator with a convincing name. The manifests in this repo apply the exact same governance a customer would configure; a real deployment swaps the simulator containers for real serving stacks and leaves every policy, subscription, and user untouched.

=== Prerequisites

* {maas} installed through xref:05-maas-models.adoc[Phase 5] of this guide
* `oc` logged in as cluster-admin
* `htpasswd`, `curl`, `jq` on PATH
* ~200m CPU and 512Mi memory per model - the whole scenario runs on one CPU node

The `cloud-models` namespace exists to make the "external cloud" side of the story visible in the URL and the UI, exactly as Fed Aura Capital's would.

The philosophy, and the line to say out loud: *caps are a property of cost, not of capability.* On-prem models run on GPUs the bank already bought - sunk cost - so their caps are generous. Cloud models are rented per token - so their caps are tight. IT gets roughly five times the standard caps because it runs the platform and the pilots.

Each division gets ONE `MaaSSubscription` covering all of its models, one API key per user, and priority 30 so the division tier outranks any shipped default subscription (see the xref:#workshop-extensions[appendix] for how the shipped tiers interact).

=== The scripts

All under `demo/corporate-scenario/`:

|===
| Script | What it does

| `setup-demo.sh`
| Builds the whole environment: 14 users, 7 groups, the `htpasswd` identity provider, the `cloud-models` namespace, all six LLMInferenceServices, and the MaaS CRDs (model refs, auth policies, subscriptions). `DEMO_PASSWORD='...'` skips the interactive prompt.

| `run-demo.sh`
| Walks the video beats from the CLI: per-division catalog visibility, one inference request per allowed model, and prints the exact base URL + API key the IDE scene needs (scene 6).

| `warmup-cloud-quota.sh`
| Burns down the cloud model's hourly quota until the next rate-limit window boundary. This is what makes scene 7 true: the 429 on camera is a real, earned exhaustion of a real cap.

| `verify-fa-cap.sh`
| The Fed Aura Capital test suite: the full 7x6 access matrix (allow/deny per cell), rate-limit behavior on the cloud models, key multiplication (limits are per subscription, not per credential), and config-drift checks that subscription caps match the matrix above.

| `cleanup-demo.sh`
| Tears everything down - CRDs, services, namespace, groups, users, identity provider. Nothing from the base guide is touched.
|===

Setup, then the video sequence:

[source,bash]
----
cd demo/corporate-scenario
./setup-demo.sh

# the video, in order:
./run-demo.sh                 # scenes 4-6 (catalogs, admin view, IDE config)
./warmup-cloud-quota.sh       # prepare scene 7 before the "55 minutes later" cut
./verify-fa-cap.sh            # prove the whole matrix holds
./cleanup-demo.sh             # when done
----

NOTE: The oauth pods restart after the identity provider is added. Wait about a minute before logging in as the demo users.

# Auth policies - one per division

== Workshop extensions (not in the video)

For live workshops where the audience gets their hands in. None of this appears in the 5-minute cut; it is here so the same environment can carry a longer session.

=== Prove the denial

The video hides unauthorized models; a workshop can also prove the enforcement. As `sales-1`, call the on-prem code model endpoint directly:

[source,bash]
----
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $SALES_KEY" \
  https://maas.<domain>/llm/opus-5-1/v1/chat/completions
# 403
----

Hidden in the catalog, denied at the API - the same policy, two faces.

=== Change a limit live

Governance is policy, not deployment:

[source,bash]
----
oc patch maassubscription fedauro-developers -n models-as-a-service --type=json \
  -p '[{"op":"replace","path":"/spec/modelRefs/1/tokenRateLimits/0/limit","value":10000000}]'
----

Re-run `./run-demo.sh` - the new cap is in effect immediately, no redeploy. Restore it the same way.

=== Key multiplication does not help

As `dev-1`, mint two keys and exhaust the shared quota with key one: key two is rate-limited the instant key one is. The limit is per subscription, not per credential. (`verify-fa-cap.sh` runs this automatically.)
