= Platform Upgrade (3.5 -> 3.6 EA2)

This page walks through moving a working {maas} deployment from {rhoai} 3.5 to the 3.6 Early Access build (`rhods-operator.3.6.0-ea.2`). Unlike the xref:12-platform-upgrade.adoc[3.4 -> 3.5 upgrade], OLM cannot perform this transition for you: the channel bump is a silent no-op and the operator has to be reinstalled. This guide covers that reinstall and the five post-install breakages that keep the DataScienceCluster from reaching `Ready`.

IMPORTANT: 3.6.0-ea.2 is an *Early Access* build published in the `beta` channel. It is not supported for production, there is no downgrade path back to 3.5, and the issues documented here are EA defects that are likely to change before GA. Use a cluster you can rebuild.

IMPORTANT: This guide is not a replacement for the official {rhoai} release notes. Always check the release notes for the latest updates.

== The Good News First

{maas} itself does not change in 3.6 EA2. Every finding on this page is about the platform *around* {maas}:

* The DSC field stays `aigateway.modelsAsAService`. No field rename, unlike 3.4 -> 3.5.
* Every {maas} component ships at the same version as 3.5.2 (`Model as a service v0.2.0`, `AI Gateway Operator v0.1.0`, `Batch Gateway v0.3.0`, `Async Processor v0.7.4`, `AI Gateway Payload Processing v0.1.0`). Only the `platform` version differs.
* `ModelsAsAServiceReady` stayed `True` through the entire operator reinstall. {maas} never went down.
* `verify.sh` scored 15/15 on 3.5.2 before the upgrade and 15/15 on 3.6.0-ea.2 after it.

What does break is TrustyAI, AI Pipelines and OGX, and because the DSC aggregates module health, any one of them keeps the whole DSC out of `Ready`.

== Prerequisites

* {maas} working on {rhoai} 3.5.x (`verify.sh` passing)
* `cluster-admin` access
* A cluster you can afford to rebuild

Confirm your starting point:

[source,bash]
----
oc get csv -n redhat-ods-operator | grep rhods-operator
oc get dsc default-dsc -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}{"\n"}'
----

[[what-changes]]
== What Changes

[cols="1,2", options="header"]
|===
| Area | Change

| *Channel*
| There is no `3.6ea2` channel. `rhods-operator.3.6.0-ea.2` is published in the *`beta`* channel.

| *Upgrade path*
| None. The `beta` channel holds a single bundle with no `replaces`, `skips` or `skipRange`, so no OLM edge exists from any 3.5.x. The operator must be reinstalled.

| *DSC MaaS field*
| Unchanged: `aigateway.modelsAsAService`. `kserve.modelsAsService` also still exists in the v2 schema.

| *New DSC fields*
| `dashboard.maasConsumerPortal` (new {maas} Consumer Portal submodule, defaults to `Removed`) and `workbenches.workbenchesV2`.

| *New DSC conditions*
| `MaaSConsumerPortalAvailable`, `WorkbenchesV2Ready`.

| *Removed DSC conditions*
| `ProvisioningProgress`, `TrainingOperatorReady`.

| *Component CRD rename*
| `datasciencepipelines.components.platform.opendatahub.io` becomes `aipipelines.components.platform.opendatahub.io`. The 3.5 CR is left behind and blocks the new one.

| *New CRDs*
| `aipipelines`, `aihubs` and `catalogs.aihub.opendatahub.io` (all `.opendatahub.io`), plus `applications.app.k8s.io`.

| *TrustyAI schema*
| The DSC declares `trustyai.eval.lmeval.permit*` as a string enum, the component CRD declares them as booleans. They disagree, which breaks the DSC.

| *Immutable fields*
| 3.6 changes the TrustyAI Deployment `spec.selector` and the OGX playground RoleBinding `roleRef`. Both are immutable, so the operator cannot patch 3.5-era objects.

| *KServe stack*
| KServe `v0.19.0` -> `v0.21.0`, vLLM `v0.24.0` -> `v0.28.0`, llm-d-router `v0.10.0` -> `v0.11.0`. New: `llm-d-autoscaling v0.9.0`, `vLLM-Omni v0.26.0`.
|===

== Step 1: Back Up Current State

[source,bash]
----
save() {  # save <outfile> <oc get args...>
  out=$1; shift
  oc get "$@" -o yaml > "$out" 2>/dev/null \
    || { echo "skipped ${out} (not present)"; rm -f "$out"; }
}

save dsc-backup.yaml       dsc default-dsc
save dsci-backup.yaml      dsci
save sub-backup.yaml       sub rhods-operator -n redhat-ods-operator
save dashboard-backup.yaml odhdashboardconfig -n redhat-ods-applications

# HTTPRoutes, in case you need to undo the Step 8 host-pinning
save httproutes-backup.yaml httproute -A

# MaaS custom resources, one kind per call
for k in maasmodelrefs maassubscriptions maastenantconfigs maasauthpolicies \
         configs.maas.opendatahub.io aitenants \
         externalproviders.inference.opendatahub.io; do
  save "backup-${k}.yaml" "$k" -A
done
----

IMPORTANT: Back the kinds up one at a time, not as a single comma-separated `oc get`. A combined call validates every type up front and aborts with `error: the server doesn't have a resource type "x"` if any one is missing, which happens on partial installs and on 3.5.0/3.5.1. The shell has already truncated the output file by then, so you are left with a 0-byte backup and no warning, one step before Step 3 deletes the operator.

Record the DSC component schema. The <<verify-schema,verification step>> re-runs this against 3.6 and diffs it, which confirms the field changes in the <<what-changes,What Changes>> table on your own cluster:

[source,bash]
----
oc get crd datascienceclusters.datasciencecluster.opendatahub.io -o json | \
  jq -r '.spec.versions[] | select(.name=="v2") |
    .schema.openAPIV3Schema.properties.spec.properties.components.properties |
    to_entries[] | "\(.key): \(.value.properties // {} | keys | join(","))"' \
  > dsc-schema-before.txt
----

[[channel-noop]]
== Step 2: Why the Channel Bump Alone Does Nothing

This is the finding that costs the most time, because nothing reports an error.

Patching the channel to `beta` appears to succeed and then has no effect:

[source,bash]
----
oc patch sub rhods-operator -n redhat-ods-operator --type=merge \
  -p '{"spec":{"channel":"beta"}}'

oc get sub rhods-operator -n redhat-ods-operator \
  -o jsonpath='channel={.spec.channel} state={.status.state} installedCSV={.status.installedCSV}{"\n"}'
----

Observed output:

[source]
----
channel=beta state=AtLatestKnown installedCSV=rhods-operator.3.5.2
----

The Subscription reports `AtLatestKnown` while sitting on 3.5.2. No InstallPlan is created, no Kubernetes event is emitted, and no condition turns `False`. This survives a forced re-resolution (`oc rollout restart deploy/catalog-operator -n openshift-operator-lifecycle-manager`).

The reason is in the catalog. The `beta` channel contains exactly one bundle with no upgrade edges:

[source]
----
channel: beta
    rhods-operator.3.6.0-ea.2                                    <- no replaces, skips or skipRange
channel: stable-3.5
    rhods-operator.3.5.2 | replaces=3.5.1 | skipRange=>=3.4.0 <3.5.2
----

You can confirm this yourself:

[source,bash]
----
oc get packagemanifest rhods-operator -n openshift-marketplace \
  -o jsonpath='{range .status.channels[*]}{.name}{"\t"}{.currentCSV}{"\n"}{end}'
----

Because `3.6.0-ea.2` does not declare that it replaces or skips any 3.5.x release, OLM finds no path from the installed CSV into the `beta` channel and quietly leaves the install alone.

IMPORTANT: `AtLatestKnown` on a channel that does not contain your installed CSV means "I found nothing I can upgrade to", not "you are up to date". Always confirm `installedCSV` after a channel change rather than trusting `state`.

== Step 3: Reinstall the Operator from the beta Channel

Deleting the Subscription and CSV removes the operator Deployment. It does *not* remove CRDs, the DSC, the DSCInitialization, or any {maas} custom resource, so your configuration and models survive.

Read the installed CSV name rather than assuming `3.5.2`, so this works from any 3.5.x patch level. Capture it *before* deleting the Subscription, and stop if it comes back empty:

[source,bash]
----
OLD_CSV=$(oc get sub rhods-operator -n redhat-ods-operator \
  -o jsonpath='{.status.installedCSV}')

if [ -z "$OLD_CSV" ]; then
  echo "installedCSV is empty - Subscription may still be resolving, or be managed by something that re-created it."
  echo "Fix that first; deleting now would orphan the old CSV."
else
  echo "removing ${OLD_CSV}"
  oc delete sub rhods-operator -n redhat-ods-operator
  oc delete csv "${OLD_CSV}" -n redhat-ods-operator --ignore-not-found
fi
----

WARNING: If the old CSV survives this step, the new Subscription fails resolution with a `constraints not satisfiable` message that points nowhere near the real cause, because another version of the operator still owns the namespace. Confirm with `oc get csv -n redhat-ods-operator | grep rhods` before moving on.

Confirm the configuration is still there before continuing:

[source,bash]
----
oc get dsc default-dsc
oc get configs.maas.opendatahub.io default
oc get maasmodelref -A
----

Recreate the Subscription on `beta`. Carry `source`, `sourceNamespace` and `spec.config` over from the `sub-backup.yaml` you took in Step 1 rather than copying the values below blindly:

[source,bash]
----
# What did the original Subscription actually use? Read the FILE, not the cluster.
# Only source and sourceNamespace carry over - NOT channel, which is the old one.
grep -E '^  (source|sourceNamespace):' sub-backup.yaml

# spec.config, if it had one
sed -n '/^  config:/,/^  [a-z]/p' sub-backup.yaml | sed '$d'
----

IMPORTANT: Read these from `sub-backup.yaml`, not with `oc get -f sub-backup.yaml`. The `-f` flag only uses the file to identify the resource and then queries the live cluster, where you just deleted the Subscription, so it reports nothing and you would silently drop `spec.config`.

WARNING: Do not carry `channel` over from the backup. The backup was taken in <<backup,Step 1>>, before anything changed, so it still says `stable-3.5`. Reusing it recreates the Subscription on the old channel and quietly reinstalls 3.5.2, and you would then work through the remaining steps against a 3.5 operator wondering why nothing matches.

WARNING: `redhat-operators` is not universal. On a disconnected or mirrored cluster the CatalogSource has a different name (see xref:00-disconnected.adoc[Phase 0: Disconnected Setup]), and a Subscription pointing at a CatalogSource that does not exist never resolves: no InstallPlan, no CSV, and you already deleted the old operator. Any `spec.config` on the original (proxy env, `nodeSelector`, `tolerations`) must be carried over too, or the new operator pod cannot reach the registry or lands on the wrong nodes.

[source,bash]
----
SOURCE_NS=openshift-marketplace
SOURCE=redhat-operators          # replace with your CatalogSource name

cat <<EOF | oc apply -f -
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhods-operator
  namespace: redhat-ods-operator
spec:
  channel: beta
  name: rhods-operator
  source: ${SOURCE}
  sourceNamespace: ${SOURCE_NS}
  installPlanApproval: Automatic
  startingCSV: rhods-operator.3.6.0-ea.2
  # Re-add spec.config here if the backup had one
EOF
----

IMPORTANT: `startingCSV` only chooses which bundle the *initial* install lands on. It does not pin the version: with `installPlanApproval: Automatic`, OLM still follows the channel head afterwards, so a later EA drop into `beta` is installed automatically. To stay on exactly `3.6.0-ea.2`, set `installPlanApproval: Manual` - but then the *first* InstallPlan also needs approving, or no CSV is ever created and you are left with no operator reconciling the DSC:

[source,bash]
----
# Only if you chose installPlanApproval: Manual.
# OLM takes 30-60s to create the InstallPlan, so poll for it.
IP=""
for i in $(seq 1 20); do
  IP=$(oc get installplan -n redhat-ods-operator \
    -o jsonpath='{range .items[?(@.status.phase=="RequiresApproval")]}{.metadata.name}{"\n"}{end}' \
    | head -1)
  [ -n "$IP" ] && break
  echo "attempt ${i}: no InstallPlan awaiting approval yet"
  sleep 10
done

if [ -z "$IP" ]; then
  echo "No InstallPlan appeared. Check the Subscription resolved at all:"
  oc get sub rhods-operator -n redhat-ods-operator -o yaml | sed -n '/^status:/,$p'
else
  echo "approving ${IP}"
  oc patch installplan "$IP" -n redhat-ods-operator --type=merge \
    -p '{"spec":{"approved":true}}'
fi
----

NOTE: Poll and take only the first match. Run immediately after the `oc apply`, the plain jsonpath returns nothing because OLM has not created the InstallPlan yet, and `oc patch installplan ""` fails with `resource name may not be empty`; with two pending plans it returns both names and fails on the malformed argument. Either way no CSV is created and nothing reconciles the DSC.

The existing OperatorGroup in `redhat-ods-operator` is reused. Now wait for the CSV to appear and reach `Succeeded`:

[source,bash]
----
INSTALLED=""
for i in $(seq 1 60); do
  PHASE=$(oc get csv -n redhat-ods-operator \
    -o jsonpath='{range .items[*]}{.metadata.name}={.status.phase}{"\n"}{end}' 2>/dev/null \
    | grep '^rhods-operator\.3\.6')
  echo "attempt ${i}: ${PHASE:-<no rhods-operator 3.6 CSV yet>}"
  if echo "$PHASE" | grep -q '=Succeeded$'; then INSTALLED=yes; break; fi
  sleep 10
done

if [ -z "$INSTALLED" ]; then
  echo "TIMED OUT - no rhods-operator 3.6 CSV reached Succeeded. Investigate before continuing:"
  oc get csv,installplan,sub -n redhat-ods-operator
  return 1 2>/dev/null || exit 1
fi
----

IMPORTANT: Match on the CSV *name*, not the version alone, and fail with a non-zero status. An AllNamespaces OperatorGroup makes OLM copy other operators' CSVs into this namespace, so a version match alone can be satisfied by an unrelated 3.6.x operator while `rhods-operator` is still `Pending`. And without the explicit `exit 1`, the timeout branch ends on a successful `oc get` and returns 0, so a pasted multi-step script walks into the next step with no operator installed.

IMPORTANT: Do not use `oc wait csv rhods-operator.3.6.0-ea.2 ...` here. OLM needs 30 to 60 seconds to resolve and create the CSV, and `oc wait` on a named resource that does not exist yet fails immediately with `Error from server (NotFound)` instead of waiting. The label-selector form fails too, with `error: no matching resources found`. Both were confirmed on a live cluster, so poll instead. Polling also survives OLM landing a later EA drop than the one you named.

NOTE: Immediately after install, `ModelRegistryReady` can fail with `no matches for kind "AIHub" in version "components.platform.opendatahub.io/v1alpha1"`. This is a start-up ordering race: the new `aihubs` CRD is not registered before the modelregistry module first reconciles. It clears on its own, so do not act on it.

At this point {maas} is already working again, but the DSC is not `Ready`. Steps 4 to 7 fix that.

[[trustyai-schema]]
== Step 4: Fix the TrustyAI Schema Mismatch

The DSC and the TrustyAI component CRD disagree about the type of two fields in 3.6.0-ea.2.

The DSC (`datascienceclusters...v2`) declares them as a *string* enum:

[source]
----
trustyai.eval.lmeval.permitCodeExecution:  type: string, enum: [allow, deny], default: "deny"
trustyai.eval.lmeval.permitOnline:         type: string, enum: [allow, deny], default: "deny"
----

The component CRD (`trustyais.components.platform.opendatahub.io/v1alpha1`) declares the same fields as *boolean*:

[source]
----
spec.eval.lmeval.permitCodeExecution:  type: boolean, default: false
spec.eval.lmeval.permitOnline:         type: boolean, default: false
----

The operator copies the DSC value straight onto the component CR, so a 3.5 DSC carrying `permitOnline: deny` produces:

[source]
----
Ready  False  Error  failure deploying resource /default-trustyai: apply failed
  components.platform.opendatahub.io/v1alpha1, Kind=TrustyAI: ... failed to create typed live object:
  .spec.eval.lmeval.permitOnline: expected boolean, got &{deny}
  .spec.eval.lmeval.permitCodeExecution: expected boolean, got &{deny}
----

This blocks `ProvisioningSucceeded` and `Ready` for the entire DSC, not just TrustyAI.

Remove the `eval` block from the DSC. Use a merge patch with `null`, not a JSON Patch `remove`:

[source,bash]
----
oc patch dsc default-dsc --type=merge \
  -p '{"spec":{"components":{"trustyai":{"eval":null}}}}'
----

That alone is not enough. The component CR created by 3.5 still holds the string values, and the operator keeps failing to apply over them. Strip it there too:

[source,bash]
----
if oc get trustyais.components.platform.opendatahub.io default-trustyai \
     >/dev/null 2>&1; then
  oc patch trustyais.components.platform.opendatahub.io default-trustyai \
    --type=merge -p '{"spec":{"eval":null}}'
else
  echo "no default-trustyai CR (trustyai is Removed) - nothing to strip"
fi
----

NOTE: Guard this with `oc get`. `oc patch` has no `--ignore-not-found` flag, so on a DSC with `trustyai: Removed` the component CR does not exist and the bare patch stops a pasted block with `Error from server (NotFound)` in the middle of the reinstall.

NOTE: A JSON Patch (`--type=json`) `remove` on these paths fails with `The request is invalid` whenever the block is already absent, which is a normal state here. The merge-patch form is idempotent: running it twice just reports `patched (no change)`. Both behaviours were confirmed on a live cluster.

The operator then repopulates the CR with correct boolean defaults. Confirm:

[source,bash]
----
oc get trustyais.components.platform.opendatahub.io default-trustyai -o jsonpath='{.spec}{"\n"}'
# Expected to include: "eval":{"lmeval":{"permitCodeExecution":false,"permitOnline":false}}
----

WARNING: Do not re-add `trustyai.eval` to the DSC on 3.6 EA2. Because the DSC field defaults to `"deny"`, setting the block at all reintroduces the string and breaks the DSC again. Leave it absent and let the component default to `false`.

[CAUTION]
====
*This guide's own Phase 4 manifest will undo this fix.* `manifests/04-rhoai-config/datasciencecluster.yaml` sets:

[source,yaml]
----
trustyai:
  eval:
    lmeval:
      permitCodeExecution: deny
      permitOnline: deny
----

Those values are correct for 3.5 and break the DSC on 3.6 EA2. Anything that re-applies that manifest puts the strings back and returns you to `expected boolean, got &\{deny}`:

* `scripts/setup-maas.sh` (it applies the manifest during Phase 4)
* a `--from-phase 3` or `--from-phase 4` resume
* re-running the `oc apply -f manifests/04-rhoai-config/datasciencecluster.yaml` from xref:04-rhoai-config.adoc[Phase 4]

On 3.6 EA2, comment the `eval:` block out of your local copy of that manifest before running any of them, and re-check the DSC afterwards:

[source,bash]
----
oc get dsc default-dsc \
  -o jsonpath='{.spec.components.trustyai.eval}{"\n"}'
# Expected on 3.6 EA2: empty
----
====

IMPORTANT: This loses any non-default LMEval permission you had on 3.5. Check what you were running before you remove the block:

[source,bash]
----
# From the backup taken in Step 1
grep -A3 lmeval dsc-backup.yaml
----

If either value was `allow`, the component now defaults to `false` and LMEval jobs lose online access and code execution.

On 3.6.0-ea.2 there is no way to get them back. Setting the value in the DSC reintroduces the string and breaks the DSC, and patching the component CR directly does not survive: the operator reverted `permitOnline: true` back to `false` within 10 seconds on a live cluster, while the DSC stayed `Ready`.

[source,bash]
----
# Does NOT work on 3.6.0-ea.2 - reverted by the operator within ~10s
oc patch trustyais.components.platform.opendatahub.io default-trustyai --type=merge \
  -p '{"spec":{"eval":{"lmeval":{"permitOnline":true}}}}'
----

If your evaluations depend on LMEval online access or code execution, this EA build cannot provide it. Plan to stay on 3.5 for that workload.

[[stale-crs]]
== Step 5: Delete Stale 3.5 Component CRs

3.6 renames the pipelines component CRD from `datasciencepipelines` to `aipipelines`. The operator creates the new CR, but the 3.5 CR is left behind and still owns shared resources, so the new module cannot adopt them:

[source]
----
AIPipelines  ProvisioningSucceeded  False  MonitoringReconcileFailed
  reconcile core ServiceMonitor: ServiceMonitor "data-science-pipelines-operator-service-monitor"
  is controlled by DataSciencePipelines "default-datasciencepipelines" with UID "7d00cfe5-..."
----

Delete the orphaned 3.5 CR:

[source,bash]
----
oc get datasciencepipelines.components.platform.opendatahub.io
oc delete datasciencepipelines.components.platform.opendatahub.io \
  default-datasciencepipelines --ignore-not-found
----

The ServiceMonitor is garbage-collected with its old owner and the `AIPipelines` controller recreates it. Confirm every condition is `True`:

[source,bash]
----
oc get aipipelines.components.platform.opendatahub.io \
  -o jsonpath='{range .items[*].status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'
----

NOTE: Use `+.items[*]+`, not `.items[0]`. Right after the delete the `AIPipelines` controller may not have created `default-aipipelines` yet, and an out-of-bounds index makes `oc get` exit 1 with `array index out of bounds` plus a dump of the whole template. `+.items[*]+` just prints nothing.

[[immutable]]
== Step 6: Fix Immutable Fields on 3.5-Era Resources

3.6 changes fields that Kubernetes does not allow to be patched in place. The operator cannot reconcile over objects that 3.5 created, and the fix in both cases is to delete the object so it is recreated.

=== TrustyAI operator Deployment (spec.selector)

3.6 drops `app.opendatahub.io/trustyai: "true"` from the Deployment's label selector, and `spec.selector` is immutable:

[source]
----
TrustyAIReady  False  DeployFailed
  Deployment.apps "trustyai-service-operator-controller-manager" is invalid:
  spec.selector: Invalid value: {"matchLabels":{"app.kubernetes.io/part-of":"trustyai",
  "control-plane":"trustyai-service-operator"}}: field is immutable
----

[source,bash]
----
oc delete deploy trustyai-service-operator-controller-manager \
  -n redhat-ods-applications --ignore-not-found
----

The operator recreates it within about 20 seconds and `TrustyAIReady` turns `True`.

=== OGX playground RoleBinding (roleRef)

3.6 tightens the SCC bound to each OGX playground from `system:openshift:scc:anyuid` to `system:openshift:scc:nonroot-v2`. A RoleBinding's `roleRef` is immutable, so every OGXServer created on 3.5 fails with:

[source]
----
OGXServer  DeploymentReady  False  DeploymentFailed
  RoleBinding.rbac.authorization.k8s.io "<name>-rb" is invalid:
  roleRef: Invalid value: {... "Name":"system:openshift:scc:nonroot-v2"}: cannot change roleRef
----

Find and delete the affected RoleBindings. They are owned by the OGXServer, so the operator recreates them:

[source,bash]
----
# List the instances and their state
oc get ogxserver -A

# Delete the stale RoleBinding for every instance (name is <ogxserver-name>-rb)
oc get ogxserver -A \
  -o jsonpath='{range .items[*]}{.metadata.namespace} {.metadata.name}{"\n"}{end}' \
  | while read -r ns name; do
      [ -n "$ns" ] || continue
      oc delete rolebinding "${name}-rb" -n "$ns" --ignore-not-found
    done
----

TIP: Drive this off the cluster rather than typing a namespace per instance. The test cluster had four OGXServers in four namespaces, and a typo in any one leaves that instance `DeploymentFailed` and the DSC `Ready=False` for a reason <<stale-conditions,Step 7>> cannot clear.

The OGX operator does not re-reconcile on its own after the delete, so nudge it:

[source,bash]
----
oc rollout restart deploy/ogx-k8s-operator-controller-manager -n redhat-ods-applications
----

Confirm the RoleBindings came back with the new role and that the instances recovered:

[source,bash]
----
oc get ogxserver -A \
  -o jsonpath='{range .items[*]}{.metadata.namespace} {.metadata.name}{"\n"}{end}' \
  | while read -r ns name; do
      [ -n "$ns" ] || continue
      printf '%s/%s roleRef=%s\n' "$ns" "$name" \
        "$(oc get rolebinding "${name}-rb" -n "$ns" \
             -o jsonpath='{.roleRef.name}' 2>/dev/null)"
    done
# Expected: roleRef=system:openshift:scc:nonroot-v2 for every instance

oc get ogxserver -A
# Expected: PHASE=Ready for every instance
----

[[stale-conditions]]
== Step 7: Clear Stale Module Conditions

3.6.0-ea.2 does not reliably re-aggregate module health after you fix the underlying resource. Conditions keep reporting an error that no longer exists, and because the DSC rolls module health up into `Ready`, the DSC stays `False` on stale data.

Two cases showed up, each needing a different nudge.

*Stale `ProvisioningSucceeded` after the TrustyAI fix.* The DSC kept quoting the `expected boolean, got &\{deny}` error after the component CR was already correct. Restarting the operator cleared it:

[source,bash]
----
oc rollout restart deploy/rhods-operator -n redhat-ods-operator
oc rollout status deploy/rhods-operator -n redhat-ods-operator --timeout=300s
----

*Stale `Degraded: UnhealthyOGXServers`.* After Step 6 every OGXServer reported `phase=Ready` with `DeploymentReady=True` and `HealthCheck=True`, but the OGX module still listed them all as unhealthy and held the DSC at `Ready=False`:

[source]
----
OGXReady  True   AllDependentsHealthy
Degraded  True   UnhealthyOGXServers: Unhealthy OGXServer instances: ns1/x, ns2/x, ns3/x, ns4/x
----

Restarting the OGX operator, restarting `rhods-operator`, and annotating the OGXServer instances all failed to clear this. Toggling the module off and back on does work.

Record the state you started from, so the second patch restores it rather than forcing `Managed` on a cluster that had OGX disabled:

[source,bash]
----
# Wait until the operator has reconciled the CURRENT generation, not just
# until Ready is True - a plain `oc wait --for=condition=Ready` returns
# instantly on the Ready=True left over from before the patch.
wait_dsc_ready() {
  local i gen obs rdy
  for i in $(seq 1 60); do
    # One atomic read, so the three values cannot come from different versions
    read -r gen obs rdy <<<"$(oc get dsc default-dsc -o jsonpath='{.metadata.generation} {.status.observedGeneration} {.status.conditions[?(@.type=="Ready")].status}')"
    echo "  generation=${gen} observed=${obs} Ready=${rdy}"
    if [ -n "$obs" ] && [ "$gen" = "$obs" ] && [ "$rdy" = "True" ]; then
      return 0
    fi
    sleep 10
  done
  echo "  DSC did not reach Ready for generation ${gen}"
  return 1
}

# What should ogx go back to? Prefer the explicit value; if the field is
# absent, fall back to whether OGXServer instances actually exist, since
# this step only applies when OGX was running.
OGX_STATE=$(oc get dsc default-dsc \
  -o jsonpath='{.spec.components.ogx.managementState}')
if [ -z "$OGX_STATE" ]; then
  if [ "$(oc get ogxserver -A --no-headers 2>/dev/null | wc -l | tr -d ' ')" != "0" ]; then
    OGX_STATE=Managed
    echo "ogx not set explicitly, but OGXServers exist - will restore to Managed"
  else
    OGX_STATE=Removed
    echo "ogx not set explicitly and no OGXServers - will leave it Removed"
  fi
fi

oc patch dsc default-dsc --type=merge \
  -p '{"spec":{"components":{"ogx":{"managementState":"Removed"}}}}'

if ! wait_dsc_ready; then
  echo "STOP: the operator never observed ogx=Removed. Do not restore yet -"
  echo "investigate with: oc get dsc default-dsc -o yaml | grep -A5 conditions"
  return 1 2>/dev/null || exit 1
fi

echo "restoring ogx to ${OGX_STATE}"
oc patch dsc default-dsc --type=merge \
  -p "{\"spec\":{\"components\":{\"ogx\":{\"managementState\":\"${OGX_STATE}\"}}}}"
wait_dsc_ready
----

IMPORTANT: The wait between the two patches is what makes this work. Without it both patches land in the same second, the operator never observes `ogx: Removed`, the stale condition is never re-aggregated, and the DSC stays `Ready=False` with no error anywhere. It has to be generation-aware: `oc wait --for=condition=Ready` has no `observedGeneration` check, so straight after a patch it returns on the previous `True` and verifies nothing.

NOTE: If `spec.components.ogx` was absent, the restore is skipped on purpose. Writing `managementState: ""` is rejected by the enum, and defaulting it to `Managed` would switch on a component the cluster never asked for, pulling in the OGX playground Deployments and the `nonroot-v2` RoleBindings from <<immutable,Step 6>>.

After the toggle the DSC reached `Ready=True` with `OGXReady=True` and all OGXServer instances still `Ready`.

NOTE: If you do not use the AI Playground, leaving `ogx` at `Removed` is a valid shortcut: it was verified to bring the DSC to `Ready=True` on its own, and {maas} does not depend on OGX.

[[portal-404]]
== Step 8: Enable the MaaS Consumer Portal (new in 3.6)

WARNING: Enabling this submodule on 3.6.0-ea.2 takes down the entire {rhoai} Dashboard with HTTP 404, including `/oauth2`, so you cannot even log in. See link:https://redhat.atlassian.net/browse/RHOAIENG-101883[RHOAIENG-101883^] (Critical). A default install is unaffected because the field defaults to `Removed`. If you do not need the portal, skip this whole step.

3.6 adds a {maas} Consumer Portal as a dashboard submodule. It defaults to `Removed`, so it is opt-in. From the CRD description:

[quote]
____
MaaSConsumerPortal controls the MaaS Consumer Portal submodule, shipped in the dashboard-operator. It is managed independently of the core Dashboard: the dashboard-operator Deployment stays up while either the core Dashboard or the portal is Managed.
____

IMPORTANT: Do the host-pinning in <<portal-prepin,Step 8a>> *before* you enable the portal. Enabling first and repairing afterwards works, but it 404s the Dashboard for everyone in the meantime. Pinning first was measured at zero downtime: 25 consecutive polls of `/` returned `302` across the whole transition, including the moment the portal HTTPRoute appeared.

[[portal-prepin]]
=== Step 8a: Host-pin the Sibling Routes First

The 404 happens because the portal's HTTPRoute is the only one on the Gateway carrying a `spec.hostnames`, which puts it in its own exact-match virtual host (see <<portal-mechanism,the mechanism>> below). The four sibling routes already exist and are hostname-less, so pinning them to the dashboard hostname now is harmless, and the portal then joins the same virtual host instead of hijacking it.

Set up the helpers and confirm the Dashboard is healthy before you touch anything:

[source,bash]
----
H=$(oc get dashboard default-dashboard \
  -o jsonpath='{.status.url}' | sed -E 's#https?://##; s#/$##')

if [ -z "$H" ]; then
  echo "could not read the dashboard hostname - stop and check 'oc get dashboard'"
  return 2>/dev/null || exit 1
fi
echo "dashboard host: $H"

check_paths() {
  [ -n "$H" ] || { echo "  no hostname - refusing to probe"; return 1; }
  for p in / /oauth2 /mlflow /catalog/ /maas-consumer-portal; do
    printf '  %-24s -> %s\n' "$p" \
      "$(curl -sk -o /dev/null --max-time 10 -w '%{http_code}' "https://${H}${p}")"
  done
}

check_paths   # /maas-consumer-portal 404s or redirects here; the other four should be 302
----

Pin the four siblings:

[source,bash]
----
apply_host() {
  [ -n "$H" ] || { echo "  refusing to pin with an empty hostname"; return 1; }
  # Only pin routes that already exist. --server-side would otherwise CREATE a
  # hostname-only HTTPRoute with no parentRefs and no rules, which attaches to
  # nothing and later collides with dashboard-operator's own Create.
  if ! oc get httproute "$1" -n "$2" >/dev/null 2>&1; then
    echo "  skipping $1 in $2 (route not present)"
    return 0
  fi
  cat <<EOF | oc apply --server-side --field-manager=maas-portal-coexist -f -
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: $1
  namespace: $2
spec:
  hostnames:
    - $H
EOF
}

apply_host rhods-dashboard      redhat-ods-applications
apply_host model-catalog        redhat-ods-applications
apply_host mlflow               redhat-ods-applications
apply_host oauth-callback-route openshift-ingress

check_paths   # the four dashboard paths must still be 302 before you continue
----

TIP: Use the `apply_host` function rather than a `for` loop over `"name namespace"` strings. zsh does not word-split unquoted expansions, so the loop form sends `name namespace` as a single resource name and every apply fails RFC 1123 validation. The function form behaves the same in bash and zsh.

WARNING: `oauth-callback-route` in `openshift-ingress` is shared. It serves the OAuth callback for *every* hostname attached to that Gateway, so pinning it to the dashboard hostname breaks login for any other host on the same Gateway - the same 404 symptom, moved somewhere `check_paths` cannot see it. Check what else that route serves before you pin it, matching any parentRef rather than just the first:

[source,bash]
----
# Which Gateways does the OAuth route attach to?
oc get httproute oauth-callback-route -n openshift-ingress \
  -o jsonpath='{range .spec.parentRefs[*]}{.namespace}/{.name}{"\n"}{end}'

# Every hostname served by those Gateways
oc get httproute -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name} parents={range .spec.parentRefs[*]}{.name},{end} hostnames={.spec.hostnames}{"\n"}{end}'
----

If that Gateway only ever serves the dashboard, as on a single-tenant install, this is safe. If it serves anything else, prefer leaving the portal `Removed` until the upstream fix lands.

=== Step 8b: Enable the Portal

[source,bash]
----
oc patch dsc default-dsc --type=merge \
  -p '{"spec":{"components":{"dashboard":{"maasConsumerPortal":{"managementState":"Managed"}}}}}'
----

Verify:

[source,bash]
----
oc get dsc default-dsc \
  -o jsonpath='{.status.conditions[?(@.type=="MaaSConsumerPortalAvailable")].status}{"\n"}'
# Expected: True

oc get deploy maas-consumer-portal -n redhat-ods-applications
----

The portal deploys as its own `maas-consumer-portal` Deployment and `maas-consumer-portal` Service (port 8443) in `redhat-ods-applications`, alongside the existing `maas-ui`.

[[portal-mechanism]]
=== Why It Breaks, and Recovery If You Already Enabled It

`dashboard-operator` creates the `maas-consumer-portal` HTTPRoute *with* `spec.hostnames` set to the dashboard hostname, while the other four routes on the same Gateway have no hostname at all. In Gateway API a hostname-less route attaches to the listener wildcard, and a route with a hostname gets its own exact-match virtual host. Envoy picks the most specific virtual host for the `Host` header and then only looks at the routes inside it, so every request to the dashboard hostname lands in a virtual host that contains only the portal paths.

If you enabled the portal before pinning, this is what you see:

[source]
----
/                        -> 404
/oauth2                  -> 404
/mlflow                  -> 404
/catalog/                -> 404
/maas-consumer-portal    -> 302
----

IMPORTANT: Every status stays green while this is broken. DSC `Ready=True`, `MaaSConsumerPortalAvailable=True`, `DashboardReady=True`, both Gateways `Programmed=True`, and the `rhods-dashboard` HTTPRoute `Accepted=True`. Nothing in any condition points at routing, so this is only visible from an HTTP request.

To recover, run <<portal-prepin,Step 8a>> now: the same `apply_host` calls fix a cluster that is already 404ing. Then `check_paths` should show all five paths at `302`.

NOTE: Removing the hostname from the portal route instead does not work. `dashboard-operator` owns `spec.hostnames` there and writes it straight back. On the other four routes it does not own that field, so a value written by a different field manager is kept.

WARNING: The pin lives only on the operator-owned HTTPRoutes, so it is lost whenever those routes are recreated: a dashboard restart or an {rhoai-short} upgrade. Re-apply <<portal-prepin,Step 8a>> and re-run `check_paths` after any of those. Toggling the portal off and on does *not* clear it - the sibling pins survived a portal removal and re-enable on a live cluster.
